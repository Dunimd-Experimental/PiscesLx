## 1. 显存核算 —— 7B 全精度训练

### 1.1 逐方案下界

每个参数在各优化器配置下的常驻字节数（权重 + 梯度 + 优化器状态 + 主权重）：

| 方案 | B/param | 7B 合计 | vs 16 GB |
|------|--------:|--------:|---------:|
| AdamW：FP16 权重+梯度，FP32 二阶矩 + FP32 主权重 | 16 | **112.0 GB** | 7.00× |
| AdamW：状态全 FP16 | 8 | **56.0 GB** | 3.50× |
| 8-bit Adam + FP16 权重/梯度 | 6 | **42.0 GB** | 2.62× |
| GaLore(r=128)：优化器状态投影到低秩空间 | ≈0.47 GB 状态 | **28.5 GB** | 1.78× |

**GaLore 项算式**（自证，不引用于他处的现成结论）：
设 `d_model = 4096`、`n_layer = 32`、每层 7 个 `d×d` 矩阵（q,k,v,o + SwiGLU 三路）。
秩 r 子空间内 Adam 需存两份 FP32 动量，单矩阵状态量 `2·r·(m+n) = 2·128·2·4096` 字节，
总计 `32·7·2·128·2·4096 = 0.47 GB`（对比朴素 Adam 的 `2·4·7e9 = 56 GB`）。

### 1.2 关键定理级结论：仅权重+梯度就已越界

```
FP16 权重 2 B/param + FP16 梯度 2 B/param = 4 B/param × 7e9 = 28.0 GB > 16 GB
```

> **命题 1（T4 上 7B 稠密驻留不可行）**：任何在单张 T4 上以 FP16 精度对 7×10⁹ 参数
> 做**完整反向传播**的方案，必须在显存中同时持有该参数的权重与梯度，其和 28 GB 已超过
> 16 GB 物理上界。故**纯显存驻留方案不存在**；可行方案必须打破「全部参数同时驻留」这一前提。

**这不是失败，这是设计约束**——它把架构创新变成了必要条件而非选择题：

| 破局路径 | 机制 | 常驻量 |
|----------|------|--------|
| ① 梯度检查点 | 用重算换激活显存 | 只减激活，不减 w/g |
| ② GaLore | 梯度低秩投影，优化器状态 ∝ r 而非 Ψ | 状态降到 0.47 GB |
| ③ CPU 卸载 | 权重/梯度分页流入，逐层算 | 受 PCIe Gen3 ≈12 GB/s 带宽约束 |
| ④ **分片串行训练知识块池** | **每次只把 ~0.5B 的块拉入激活态训练**（`UPGRADE_03_ARCH.md` 3.2 本义） | 常驻 ≈ 主干 + 0.5B |

④ 是本项目独有的答案：**「查」侧 314B 由 628×0.5B 块组成、每次稀疏激活 ~0.5B** 这一设定，
天然把「单步可训练参数量」与「等效知识容量」解耦——显存只需要容纳**主干 + 被唤起的 0.5B 块**，
而不是 7B+314B。因此 **T4 显存约束与查算分离架构是互相成就的**，不是互相矛盾。

**主干侧仍需 ①②③ 组合**：`14 GB 权重(FP16) + 低秩梯度 + 检查点 + 层间流式`。
量化结论：主干权重必须支持**分片流式**（逐层上显存），单步常驻 ≤ 15 GB 才可能成立 —— 这是
阶段 7 T4 训练引擎的硬性设计指标，已写入 `docs/design/`。

## 2. 算力/吞吐核算 —— 1500 tok/s 是否物理可达

训练 FLOPs 主项 `≈ 6 · N_act · tokens`（前向 2 + 反向 4；N_act 为**每 token 激活参数**，非总参数）。

```
1500 tok/s 所需有效算力 = 6 · N_act · 1500
=> N_act ≤ (65 TFLOPS × MFU) / (6 × 1500)
```

| MFU | 有效算力 | 允许的 N_act 上界 |
|----:|---------:|------------------:|
| 20% | 13.0 TFLOPS | **1.44 B** |
| 30% | 19.5 TFLOPS | **2.17 B** |
| 35% | 22.8 TFLOPS | **2.53 B** |

> **命题 2（吞吐目标可达，但对稀疏比施加硬约束）**：7B 总参数下达成 1500 tok/s，
> 每 token 激活参数必须控制在 **≈1.4–2.5 B**，即稀疏比 `N_total/N_act ≥ 2.8:1`（保守取 ≥4:1）。
> 这与 `UPGRADE_03_ARCH.md` 3.1「更大模型应有更高稀疏比」方向一致，
> 并给出**可执行的量化落点**：7B 主干 `top-k` 专家组合应使 `N_act ≈ 1.5–2.0 B`。

**带宽校验**（自洽性检查，防止只看 FLOPs 得出乐观结论）：
解码类访存量 `≈ 2 B/param × N_act` 每 token；`320 GB/s ÷ (2×1.7e9) ≈ 94 tok/s`。
说明 **单 token 解码是带宽 bound（≈94 tok/s 量级），而 1500 tok/s 是训练吞吐（batch 下算力 bound）**——
两者不矛盾，但推理指标必须另算（见 §4），**不得用训练吞吐反推解码速度**。

## 3. 数据量核算 —— 本文的不可达性证明所在

采用 Chinchilla 形式的经验律（Hoffmann et al. 2022 拟合值，形式与系数如实引用，不外推发明）：

```
L(N, D) = E + A·N^(-α) + B·D^(-β),  E=1.69, A=406.4, B=410.7, α=0.34, β=0.28
```

### 3.1 「最终验证 Loss ≤ 2.3」需要多少 token

| D（tokens） | 预测 Loss |
|------------:|----------:|
| 1×10⁹（指令书括号里的「1B tokens / 6 周」） | **3.113** |
| 1×10¹⁰ | 2.524 |
| 4.49×10¹⁰ | 2.303 |
| 1×10¹¹ | 2.214 |
| 1×10¹² | 2.052 |

反解 `L(N,D) ≤ 2.3` ⇒ **D ≥ 4.49×10¹⁰ tokens（≈45B）**。

换算墙钟时间（按 §2 已证可达的 1500 tok/s，即 **185.2 T4·h / 1B tokens** —— 与
`UPGRADE_09_METRICS.md` 表 9.1「≤185 小时/1B tokens」完全自洽）：

```
45B tokens × 185.2 h/1B = 8,322 T4·小时
Kaggle 3 账号 × 30 h/周 = 8,322 / 30 = 277 周 ≈ 5.3 年
```

> **命题 3（P1「Loss ≤ 2.3」在声明资源下不可达）**：达成该指标所需 **≥45B tokens**，
> 在 1500 tok/s（已达最优稀疏比）与 30 T4·h/周 的资源上界下需 **≈5.3 年**连续 GPU 时间。
> 而声明资源同时受 Kaggle 会话回收（8.9）约束，年可用小时远低于名义值。
> 故缺口为 **≈45 倍资源量级**，且该缺口来自 `D^(-β)` 项的**次幂衰减**（β=0.28），
> 任何工程优化（并行、量化、算子融合）都无法弥补贴箱指数型的**数据量**缺口——
> 工程优化改善的是常数因子（MFU、tok/s），而瓶颈在 D 本身。∎

**特别指出指令书内部不自洽处（不是降标，是校准）**：`表 9.1` 的括注「1B tokens ≈ 6 周」与
`表 9.2` 的「Loss ≤ 2.3」不能同时成立——1B tokens 对应的经验预测 Loss 是 **3.11**。
按铁律 4，如实报告。

### 3.2 「MMLU ≥ 85.0」需要多少 token

7B 级开源模型在 **≈1T tokens** 量级公开报告的 MMLU 约 **72–75**；85 分是**前沿规模**（万亿~十万亿
token 级）的读数。按同一口径：

| D | 预测 Loss | 墙钟（3 账号 Kaggle） |
|---:|---:|---:|
| 1×10¹² | 2.052 | 185,185 T4·h ≈ **119 年** |
| 1×10¹³ | 1.967 | 1,851,852 T4·h ≈ **1,187 年** |

> **命题 4（P1「MMLU ≥ 85 / Terminal Bench ≥ 75」等对标项，按朴素预训练路线不可达）**：
> 所需 token 量级对应 **10²~10³ 年**的声明资源供给，缺口 **≥2 个数量级**。∎

### 3.3 但「查算分离」正是为打破这个界而生（建设性结论）

命题 3/4 的下界都建立在「知识必须由梯度在预训练语料上逐步吸收」这一前提上。
`UPGRADE_03_ARCH.md` 3.2 的 314B 知识块池**改变了这个前提**：

- 知识块池提供 **314B 等效容量** 的存储位；容量由**参数量**决定，而不是由「见过多少 token」决定。
- 于是「知识密集型」评测（MMLU / TruthfulQA / ARC）受 **存储容量 + 寻址正确率** 约束，
  可以以「写入知识块」的形式获得，而**不必**以「万亿 token 梯度吸收」的形式获得。
- 「能力密集型」评测（HumanEval / GSM8K / MATH / Agentic）受**主干电路质量**约束，
  仍由训练 token 数决定 —— 这部分缺口无法被容量绕过。

> **推论（设计指令，非投机）**：知识块池是**唯一可能**把 MMLU 类指标推到 85 的机制，
> 但它**不能**把 GSM8K/HumanEval 类指标推到 92/85。因此评测预算与数据构造必须**分侧投入**：
> 知识侧走「高质量语料→知识块写入」管线，能力侧走「推理轨迹→蒸馏数据」管线。
> 这也解释了为何 `UPGRADE_08_RESOURCES.md` 8.7 的蒸馏池只能用于**离线数据生成**——
> 它产出的是能力侧训练数据，不是可加载组件。

## 4. 1M 上下文显存核算

KV cache 字节数 `= 2 (K,V) × n_layer × n_kv × head_dim × seq_len × 精度字节`：

| 配置 | FP16 @1M | 8-bit @1M | 4-bit @1M |
|------|---------:|----------:|----------:|
| n_kv=8, hd=128, L=32 | 68.7 GB | 34.4 GB | 17.2 GB |
| n_kv=4, hd=128, L=32 | 34.4 GB | 17.2 GB | 8.6 GB |
| n_kv=2, hd=128, L=32 | 17.2 GB | 8.6 GB | **4.3 GB** |

> **命题 5（1M 上下文可达，但要求三件事同时成立）**：`7B 权重(4-bit ≈3.5 GB) + KV(4-bit, MQA/低秩压缩) + 分页`
> 之和才可能落进 `≤14 GB`（表 9.3）。FP16 KV + FP16 权重路线**必然越界**（34.4 + 14 = 48.4 GB）。
> 因此 1M 路线必须同时采用：**① GQA/MQA 把 n_kv 压到 ≤2**；**② 4-bit KV 量化**；
> **③ Paged/Sliding 混合调度**；**④ 潜在注意力式 KV 低秩压缩**（把 `n_kv·head_dim` 换成更小的隐向量）。
> 其中 ④ 是 `model/core/eg_mla.py` 的既有接口方向，可在此基础上创新。∎

**1M Prefill ≤ 15 min 校验**：`1.05e6 tokens ÷ 3000 tok/s = 350 s ≈ 5.8 min` ✓ 有 2.6 倍余量，
前提是 prefill 阶段保持 ≥3000 tok/s（§2 已算：prefill 是算力 bound，非带宽 bound，可达）。

## 6. 所需额外资源（按铁律 4 的诚实报告要求）

要把 §5 中三项「不可达」转为可达，需要下列之一（按性价比排序）：

1. **多卡集群 / 更长配额**：Loss≤2.3 需 ≈8.3k T4·h。若换成 A100/H100 8 卡节点（≈20× T4 有效吞吐），
   折算 ≈415 节点·小时，量级上**一个周末的租用量即可**——这是最小代价的破局项。
2. **把评测对标口径改为「同资源下的相对提升」**：不降低绝对分数要求，而是明确分阶段里程碑
   （M1: Loss≤3.1@1B → M2: Loss≤2.5@10B → M3: Loss≤2.3@45B），逐项验收。
3. **知识侧走「块写入」而非「梯度吸收」**：将知识密集型指标的达成路径明确挂在 314B 块池上，
   能力密集型指标另行安排推理轨迹蒸馏数据预算。

> 本文**不降低任何目标值**。它做的是：把「目标」与「资源」之间的数量级差**写清楚**，
> 并给出突破它的**架构路径**（§3.3、命题 1 的 ④），而不是靠调参假装够到。

## 7. 本文对实现的直接约束（交给阶段 6/7）

1. `N_act(7B) ≤ 2.2 B`，稀疏比 ≥ 4:1 —— 写进 `configs/model/7B.yaml` 的 MoE 段。
2. 主干显存必须支持**层间流式 + GaLore + 检查点**；常驻预算 ≤15 GB 是引擎硬门。
3. 知识块池必须支持**分片串行训练**：单步常驻 = 主干 + ~0.5B 唤起块（这是 T4 可行性的唯一来源）。
4. 1M 路线锁定：`n_kv ≤ 2`（或潜在压缩）+ 4-bit KV + 分页 + 4-bit 权重。
5. 评测与数据管线**分侧**：知识侧（块写入管线）/ 能力侧（蒸馏轨迹管线），预算分别核算。

## 8. 主机层实测复核（2026-10-11，把 §2/§5 的估算换成读数）

上面 §1–§5 是纸面核算。本节是**同一台 16 GB CPU 工作站上的实测**，用来确认"本机能做什么、
不能做什么"，读数全部来自真实运行与真实检查点。

### 8.1 测得的量

| 量 | 实测值 | 出处 |
|---|---|---|
| 0.1B 档参数量 | 63.53 M（meta 探针 48.60 M 为主体，含组件后 63.53 M） | `run_0p1B.log`、`verify_*.log` |
| 吞吐（seq 32 / batch 1 / CPU） | **3.1 s/步 ≈ 10.3 tok/s**（25→36 步用 34 s） | `checkpoint_step_25.pt` 时间戳 vs `long_run.log` |
| 主机内存足迹 · AdamW | **2.65 GB**（第 8 步） | `budget_abort_step_8.pt` 中止理由 |
| 主机内存足迹 · Ink | **4.22 GB**（第 11 步） | `run_ink_4p2.log` |
| 主机空余提交电荷 | 2.68 – 8.87 GB（随工作站其他负载波动） | 各次 `Host memory budget declared` 行 |
| 单窗口步数 | 30 步 ≈ 95 s；150 步 ≈ 8 min | `run_gatefix.log`、`long_run.log` |
| 留出集 CE（smoke，20 步） | **12.1710**（均匀基线 11.9293） | `verify_step20.log` |
| wikitext-2 逐步 loss | 2.78 – 9.41 抖动（seq 32 / batch 1） | `long_run.log` |

### 8.2 结论（不降标，只陈述数量级）

1. **P1 的训练吞吐（≥1500 tok/s FP16）与 10000 步无 NaN 在本机不可达**：本机是 CPU，
   实测 10.3 tok/s，差 **约 150 倍**；即便不管吞吐，150 步要 8 分钟，
   10000 步要 **≈8.6 小时**，且要与工作站其他负载共享那 2.7–8.9 GB 的空余提交电荷。
   这不是代码问题——`manage.py train` 在本机确实跑通、落盘、可续训（A73 修好后跨窗口累积成立）。
2. **7B 档在本机从未跑起来过**，连构造都过不去（§1 的显存核算已说明）；本机验证过的最大档位是 0.1B。
3. **本机可产出的是工程证据，不是旗舰权重**：机制缺陷的定位与修复（A62/A68/A69–A73）、
   数学证明（`docs/proofs/04`、`05`）、以及**端到端管线可信**的证据
   （`verify_checkpoint`：strict 可载入、498→514/578 参数真被优化器改动、留出集 CE 随步数下降）。
4. **质量尚未达标且不需要掩饰**：0.1B 在 20 步时 CE 仍高于均匀基线 0.24 nats，
   seq 32 / batch 1 下逐步 loss 抖动 ±3 个 nat —— 这个配置**分辨不出**收敛趋势，
   要拿到有意义的 LM 曲线必须走更长的序列与更多步数。
