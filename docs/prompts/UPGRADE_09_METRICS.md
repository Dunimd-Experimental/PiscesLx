# 09 · 硬性指标 · 自主迭代 · 数学证明 · 自主架构探索

以下指标为**硬性验收标准**，不是参考值。7B 模型必须达到或超过。

### 指标优先级分层（P0 / P1 / P2）

指标按优先级分三层。**达标顺序：先 P0，再 P1，最后 P2。** 较低的层级未全部达标时，不得以"已达到高层次"为由忽略低层次。

| 层级 | 定义 | 达标要求 | 涉及指标 |
|------|------|----------|----------|
| **P0（底线，不可妥协）** | 正确性 / 真实性 / 可复现性 / 交付完整性 | **必须 100% 满足**，否则任务不成立 | 交付真实权重；真实训练非伪造；无 mock/造假；权重上传 HF+ModelScope；源码备份 Gitee+GitHub；强制编码规范；MoE 非 Dense；查算分离为模型自身权重；模态为 4 种；数学证明正确 |
| **P1（核心能力，逼近旗舰）** | 训练可达 + 核心评测逼近 DeepSeek-V4-Flash-0731 | **必须全部达标**，未达标则继续自主迭代 | 训练速度（9.1）；训练结果（9.2）；核心评测项（9.4 中 Terminal Bench / MMLU / HumanEval / GSM8K 等）；推理速度（9.3）；1M 上下文 |
| **P2（尽力而为，持续逼近）** | 次要评测项 + 极限优化 | **尽力达成，未达标需诚实报告差距**（见 `UPGRADE_01_ROLE.md` 诚实原则） | 边缘评测项；极限显存/延迟优化；额外模态质量提升 |

> **意义**：分层不是降低标准，而是**明确达标顺序与失败处理**——P0 不容许任何妥协（这是"求真"的底线），P1 必须靠创新死磕到达标，P2 允许诚实报告差距。任何层级都不允许伪造达标。

## 9.4 评测指标（对标 DeepSeek-V4-Flash-0731，必须接近其真实水平）

**7B 的评测结果必须接近 DeepSeek-V4-Flash-0731 的真实水平。不是"差不多"、不是"及格"，而是逼近。目标定为对标水平的 85%~95%，多个核心项必须 ≥ 90%。**

> **为什么定这么高**：只有定到接近顶尖旗舰的水平，你才必须进行"真正的创新"——全新的架构、全新的算法、更优的实现——而不是简单算法优化。低目标不会激发进化，高目标才是进化的唯一驱动力。

### 分数是手段，创新是目的

**这些分数不是最终目的，而是逼迫你进行"进化"的手段。** 如果只做算法优化就能达标，说明目标还不够高。真正的目标是：**全新架构**（重新设计模型的组织方式）、**全新算法**（发明前所未有的机制）、**更优实现**（同样能力下质的效率提升）。

达不到上述分数 → 说明创新不够 → **必须继续自主迭代，直到达标，不允许停止、不允许降低目标**。

## 9.5 强制自主迭代机制（核心要求）

**你必须建立自主迭代闭环，直到所有硬性指标达标。** 这不是"跑一次评测就交差"，而是：

```
设计 → 实现 → 训练 → 评测 → 分析差距 → 创新改进 → 重新训练 → 重新评测 → ...
         ↑                                                              ↓
         └──────────────── 直到全部达标才停止 ─────────────────────────┘
```

**迭代要求**：
1. **自主驱动**：不需人指示，自己发现问题、自己提出改进方案、自己验证
2. **创新驱动**：每次迭代必须是"实质性的架构/算法创新"，不是简单调参
   - 禁止：只调学习率、只改 batch size、只换优化器参数
   - 必须：改架构、换机制、引入全新算法、重新设计数据流
3. **永不降标**：达不到目标时只能向上迭代（提升能力），禁止下调目标
4. **记录留痕**：每次迭代必须留痕——假设、改动、结果、分析、下一步
5. **收敛判据**：只有当所有硬性指标（9.1~9.4）全部达标，迭代才结束
6. **迭代上限**：没有上限。需要多久就迭代多久，直到达标

**创新的定义（必须区别于"优化"）**：

| 范畴 | 不算创新（禁止拿来交差） | 算创新（必须做到） |
|------|------------------------|-------------------|
| 架构 | 调整层数/维度/头数 | 重新设计 MoE 路由/查算分离注入/模态统一框架 |
| 算法 | 调学习率/换优化器 | 发明新的注意力/寻址/融合机制 |
| 实现 | 加个 wrapper/换名 | 相同能力下数量级的效率提升 |
| 系统 | 调 batch/精度 | 全新的显存管理/知识调取方案 |

**一句话：优化是在已有轨道上跑得更快，创新是铺一条新轨道。你必须铺新轨道。**

## 9.6 评测执行要求

- 所有评测**必须真实运行**，禁止使用预存结果或模拟分数
- 评测脚本必须可复现：任何人拿到代码后可在 T4 上复跑
- 评测结果需附完整日志（输入/输出/分数/耗时）
- 与 DeepSeek-V4-Flash-0731 的对比需在相同评测条件下进行
- 缺失的评测项（如平台不支持）需明确说明原因，不能跳过
- **每轮迭代的评测结果都必须归档留痕**，形成完整迭代轨迹

## 9.7 强制性数学证明要求（核心要求）

**你的每一项创新——无论是新架构、新算法、新机制——都必须附带严格的数学证明。** 这不是"写几句解释"，而是**真正的数学证明**。拍脑袋说"这样应该更好"是不允许的。

### 9.7.1 必须证明什么

1. **正确性证明**：证明机制在数学上正确
   - 复杂度分析：时间/空间复杂度的严格推导（大 O 记号）
   - 收敛性证明：涉及优化/训练过程时，需证明或引用收敛性结论
   - 梯度稳定性：可训练模块需分析梯度是否爆炸/消失（雅可比谱分析、Lipschitz 常数界）
   - 数值稳定性：浮点误差分析，说明为什么不会数值溢出/下溢
2. **有效性证明**：证明机制为什么能提升能力
   - 表达能力：证明比被替代的旧机制表达力更强（或至少不弱）
   - 信息论分析：涉及知识注入/压缩时，用信息论（互信息、熵、率失真）说明信息损失下界
   - 建模假设：明确前提假设，并在假设下证明结论
3. **必要性/最优性论证**：证明为什么必须这么做
   - 若声称某设计吞吐/显存最优，需推导下界并证明达到下界
   - 若声称某容量（如 314B 等效）紧凑，需证明压缩效率的理论极限
4. **与现有方法的对比证明**：数学上说明你的方法为何优于现有论文方法

### 9.7.2 证明的强制标准

- **必须正确**：逻辑无漏洞、无循环论证、每步有依据。**错误的证明等同于没有证明，甚至更糟**
- **必须真实**：禁止编造定理、伪造推导、"证明显然成立"式敷衍、引用不存在的论文
- **必须可验证**：任何人能按推导逐步复核。每步推导写清依据（定义/引理/定理/已知结论）
- **必须留痕**：所有证明以 Markdown 写出，归档到对应文件夹（如 `docs/proofs/` 或模块目录），并注明对应代码实现位置

### 9.7.3 证明与实现必须绑定

- 每个创新点：**数学证明 ↔ 代码实现**必须一一对应、可互相追溯
- 若代码实现与证明不符（如做了额外近似），必须说明近似位置、误差界、为什么可接受
- 提交前必须自查：证明的结论是否真被代码实现？实现是否真满足证明的前提？

### 9.7.4 不符即不通过

- **证明错误的创新点不予采纳**：机制的证明有逻辑错误，必须修订机制或证明直到正确
- **无证明不算创新**：任何"创新"若没有配套的、正确的数学证明，一律不算创新，不能作为验收依据

## 9.8 自主架构探索：不只是 MoE（核心要求）

**MoE 稀疏专家只是"当前已知的一条路径"，绝不是唯一路径。** 未来的架构不会只有 MoE 一条路。你被授权并鼓励**自主探索、自主发明全新的架构范式**。

### 9.8.1 你必须自主探索
- **不被现有架构束缚**：允许跳出 MoE 框架，探索全新的参数组织方式
- **允许自主增加架构组件**：现有架构不足以支撑目标（7B 逼近旗舰、1M 上下文、T4 全精度训练）时，可自主新增架构组件——全新模块、全新计算范式、全新参数组织
- **允许自主开辟新路径**：MoE、查算分离、SSM、混合注意力……都只是"已知地图"上的点。你有权去地图之外探索

### 9.8.2 但不允许冗余
- **禁止功能重叠**：新增组件不能与已有组件功能重复（如不能同时存在两个作用相同的路由机制）
- **禁止堆砌**：不能为"看起来创新"而加入无意义组件。每个组件必须有其不可替代的作用
- **合并优先**：新思路与旧组件重叠时，应合并升级，而非并存
- **正交设计**：理想情况下各组件正交互补，各负责不同能力维度

### 9.8.3 目标：既精简又强大
- **不冗余**（避免堆砌、功能重叠、参数浪费）
- **强能力**（充分发挥每份参数的潜力，能逼近旗舰、能支撑全模态、能处理 1M 上下文）

**真正的进化 = 在不冗余的前提下发挥出更强大的能力。** 只增加组件叫堆砌，只做减法叫退化，**既做加法又做减法、在更精简的结构里爆发出更强的能力，才叫进化**。

必须同时满足（缺一不可）：只堆砌不精简 → 违背不冗余；只精简不探索 → 违背创新；**又精简又强大 → 这才是被期待的进化**。

### 9.8.4 MoE 仍然必须保留
- 所有规模（0.5B ~ 1T）**仍然必须是 MoE 稀疏专家模型**
- MoE 是最底层基础，你可以在此基础上**叠加、组合、发明**新架构范式
- 允许的探索包括：与 MoE 正交的新组件、MoE 之上的新组织方式、超越 MoE 的新范式（但必须保证 MoE 特性——稀疏专家激活——不被破坏）
