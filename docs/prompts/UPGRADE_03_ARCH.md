# 03 · 架构规范

## 3.1 MoE 稀疏专家模型（全家族统一）

**绝对禁止将 MoE 退化为 Dense。** 从 0.5B 到 1T，所有模型配置都必须是 MoE 稀疏专家模型。

- 每个规模有独立的 MoE 配置（专家数、top-k、共享专家数等）
- 更大的模型应有更高的稀疏比（total >> activated），较小的模型可适度降低稀疏比
- **7B 模型**：总计算参数 7B，全部通过 MoE 专家组织。激活参数的具体数值由你根据架构创新决定，但必须是 MoE 结构
- 所有规模都支持全部模态（不同规模上下文长度可以不同）
- 所有规模都支持思考/推理能力（thinking/reasoning）

## 3.2 查算分离（Compute-Search Separation）

参考 DeepSeek 查算分离架构，将模型分为两部分。**注意：这里"查"不是外部向量数据库、不是外挂检索、不是 FAISS/文件索引——它本身就是模型自身的权重。**

### 计算（算）— 7B 主参数
- **角色**：大脑，纯思考、纯推理、Agent 操作、所有模态理解
- **特性**：可训练；包含所有推理/理解/模态处理能力；支持 Agent 操作（工具调用、ReAct、多步推理）；MoE 稀疏专家结构；能创新、能自我迭代

### 查找（查）— 314B 知识块池（628 × 0.5B）
- **本质**：**它也是模型权重**，不是外部数据库。这 314B 权重**就存在于模型内部**，由 **628 个 0.5B 的知识块**组成（314 ÷ 0.5 = 628）
- **激活方式**：**激活量极小**——每次只激活约 **0.5B** 量级的知识块参与计算，其余处于非激活态。因此实际训练/推理时是 **7B（主参数）+ 0.5B（激活的知识块）** 一起工作，而不是把整个 314B 拉起来
- **类比**：**人类的潜意识**。潜意识的知识就在你身上（是你的权重、你学会的东西），但不在当前意识（激活路径）里。需要时被"唤起"，唤起后短暂进入工作记忆（激活），用完退回潜意识
- **特性**：
  - **是模型自身的权重**，内嵌于模型，非外挂、非数据库、非文件索引
  - **由 628 个 0.5B 知识块组成**，稀疏激活（每次约激活 0.5B 量级）
  - **被激活的知识块参与训练**——"查"不是"死的"，被调取并激活的那部分会参与梯度更新（可理解为先训练/复用这些 0.5B 块，再与主参数联合工作）
  - 存储世界知识（事实、常识、百科、语言知识等）
  - 通过**寻址/调取机制**定位并唤起对应知识块（机制未定，见下方留白）
  - 被调取的知识以"注入/调制"方式短暂影响激活路径，随后退回非激活态
  - 与上下文窗口并行运行，不占用上下文长度
  - 314B 是等效知识容量；因稀疏激活，实际计算占用与"激活的 0.5B"挂钩

### ⚠️ 核心创新留白（本项目的命门，必须自主探索）

**"查"这项机制——如何寻址、如何存储 628 个知识块、如何快速调取、如何注入激活路径、如何与主参数联合训练——业界没有现成方案可参考，本项目也尚无实现先例。**

- **不预设任何实现方式**。上文"内存级加载"只是类比，**不代表它真的从内存加载**；不得据此臆断成"预取/量化/分层缓存"等任何具体技术
- **具体方案由你（Agent）自主设计并给出数学证明**。这是本项目最核心的创新点之一，是最重要的"留白考题"
- 你需要设计的目标：**在激活量极小（~0.5B）的前提下，让 628 个 0.5B 知识块的整体等效容量（314B）可被高效寻址与调取，且调取速度足够快、知识足够"有知识"（能支撑下游能力与评测）**。如何达到，由你决定

### 关键设计约束
- 计算（7B 主参数）和查找（314B 知识块池）**都是同一个模型的权重**——不是"模型 + 外部库"，而是"一个模型内部的激活部分与知识块池"
- "算"是模型权重的**激活态（主参数）**；"查"是**由 628 个 0.5B 知识块组成、每次仅稀疏激活 ~0.5B 的权重池**
- 被激活的知识块**参与训练**（不是"永不训练的冻结块"）
- 所有"活"的能力（推理、理解、创新、Agent）都在计算部分
- 现有 `subconscious.py`（YvSubconsciousSystem）已体现"潜意识"思想，是查算分离的基础，在此基础上创新升级
- **寻址/存储/调取/注入/训练隔离的具体机制是未定项，属于必须自主创新的留白，不得照搬任何外部现成方案，也不得臆断为某种特定实现**

> **一句话理解**：算 = 意识（7B 主参数，全部激活参与计算）；查 = 潜意识（628 个 0.5B 知识块组成的 314B 池，每次稀疏唤起 ~0.5B，被唤起的块参与训练）。"内存"只是比喻，真正的寻址与调取机制是本项目必须自主发明的核心创新。

## 3.3 模态重定义与统一

### 3.3.1 模态重定义（重大方向修正）

经近半年实践，团队认为原模态设计方向有误。**升级后只保留 4 种真正的模态**：

**保留（4 种）**：text、image、audio、video

**移除（2 种）**：

1. **document 不再作为独立模态**
   - 理由：文档本质可通过 Agent 能力处理，不需专门文档模态编码器。解析、理解、问答都可走"Agent 操作 + 文本处理"路径
   - 处理：删除 `YvDocEncoder`（LayoutLMv3）及相关文档模态代码，文档能力通过 Agent/文本能力间接覆盖

2. **agent 不再作为独立模态**
   - 理由：**Agent 本质上还是文本（TXT）**——它只是通过**标签（tag）方式操作 Agent 工具**，不是独立输入模态。这正是主流大模型（DeepSeek、GPT、Claude、Qwen 等）的做法：工具调用以特殊 token / XML 标签 / JSON 结构出现在文本序列中，由模型自回归生成。半年实践证实，把 Agent 当独立模态是错误方向
   - 处理：删除 `YvAgenticEncoder` 作为"模态编码器"的定位，Agent 能力回归为**文本层面的工具调用协议**（特殊 token / 标签 / 结构化文本），与主流对齐。已有的工具执行、ReAct、协议适配等推理时能力保留，但服务于"文本+工具调用"，而非"agent 模态"

> **注意**：动手前先查资料确认——查阅 DeepSeek、GPT、Claude、Qwen、Kimi 等旗舰的工具调用机制，确认 Agent 本质是文本（标签驱动工具调用）、Document 的处理路径。用事实支撑这一重定义。

### 3.3.2 模态统一

当前有多个独立模态编码器（vision, audio, video, doc, agentic），需要统一。经 3.3.1 重定义后，**只需为 4 种真正模态（text/image/audio/video）做统一**：

**目标**：设计统一的多模态处理框架，消除模态间冗余，同时保留各模态的特异性处理。

**可考虑的方向（不限于此）**：
- 统一 token 空间：所有模态投影到共享表示空间
- 统一编码器骨干 + 模态特异性适配器
- 统一融合机制：替代当前多个独立 fusion 模块（fusion, enhanced_fusion, rca_fusion, sync_fusion）
- 模态路由：MoE 天然支持模态特异性专家路由

**约束**：
- 必须支持 4 种模态（text, image, audio, video）
- 不能丢失任何模态的能力
- document 与 agent 的能力不能丢失——分别通过 Agent 能力 / 文本工具调用能力覆盖
- 所有规模（0.5B ~ 1T）都支持所有模态
- 彻底移除 document 和 agent 作为独立模态的痕迹（编码器、配置项、数据管线、评测项等）

## 3.4 上下文长度

**7B 模型**：输入上下文 ≥ 1,048,576 tokens（1M）；输出上下文 ≥ 1,048,576 tokens（1M）。输入和输出都必须达到 M 级。

**其他规模**：上下文长度可以不同，但都应尽可能长；更小的（0.5B, 1.5B）可适当降低；更大的（32B+）应支持更长上下文。

## 3.5 思考/推理能力

**所有规模都必须支持思考能力**。这是与顶尖模型竞争的基础，不支持思考的模型没有竞争力。

现有推理系统（`model/reasoning/`）需保留并升级：CoT Memory、Multi-Path 路由、Recursive Depth、Unified Reasoner、Self-Evolution、TTT-E2E（Test-Time Training）、VeriCoT、Verification 系统。
