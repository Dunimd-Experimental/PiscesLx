## 三、架构规范

### 3.1 MoE 稀疏专家模型（全家族统一）

**绝对禁止将 MoE 退化为 Dense。** 从 0.5B 到 1T，所有模型配置都必须是 MoE 稀疏专家模型。

- 每个模型规模都有独立的 MoE 配置（专家数、top-k、共享专家数等）
- 更大的模型应有更高的稀疏比（total >> activated），较小的模型可以适度降低稀疏比
- **7B 模型**：总计算参数 7B，全部通过 MoE 专家组织。激活参数的具体数值由你根据架构创新决定，但必须是 MoE 结构
- 所有模型规模都支持全部模态（不同规模的上下文长度可以不同）
- 所有模型规模都支持思考/推理能力（thinking/reasoning）

### 3.2 查算分离（Compute-Search Separation）

参考 DeepSeek 的查算分离架构，将模型分为两部分。**注意：这里的"查"不是外部向量数据库、不是外挂检索、不是 FAISS/文件索引——它本身就是模型自身的权重。**

#### 计算（算）— 7B 主参数
- **角色**：大脑，纯思考、纯推理、Agent 操作、所有模态理解
- **特性**：
  - 可训练
  - 包含所有推理能力、理解能力、模态处理能力
  - 支持 Agent 操作（工具调用、ReAct、多步推理）
  - MoE 稀疏专家结构
  - 能够创新、自我迭代

#### 查找（查）— 314B 知识块池（628 × 0.5B）
- **本质**：**它也是模型权重**，不是外部数据库。这 314B 权重**就存在于模型内部**，由 **628 个 0.5B 的知识块**组成（314 ÷ 0.5 = 628）。
- **激活方式**：**激活量极小**——每次只激活约 **0.5B** 量级的知识块参与计算，其余知识块处于非激活态。因此实际训练/推理时是 **7B（主参数）+ 0.5B（激活的知识块）** 一起工作，而不是把整个 314B 都拉起来。
- **类比**：**人类的潜意识**。潜意识的知识就存在你身上（是你的权重、你学会的东西），但不在当前的意识（激活路径）里。需要时被"唤起"，唤起后短暂进入工作记忆（激活），用完又退回潜意识。
- **特性**：
  - **是模型自身的权重**，内嵌于模型，非外挂、非数据库、非文件索引
  - **由 628 个 0.5B 知识块组成**，稀疏激活（每次约激活 0.5B 量级）
  - **被激活的知识块参与训练**——"查"不是"死的"，被调取并激活的那部分知识块会参与梯度更新（可理解为先训练/复用这些 0.5B 知识块单元，再与主参数联合工作）
  - 存储世界知识（事实、常识、百科、语言知识等）
  - 通过**寻址/调取机制**定位并唤起对应知识块（机制未定，见下方"核心创新留白"）
  - 被调取的知识以"注入/调制"方式短暂影响激活路径，随后退回非激活态
  - 与上下文窗口并行运行，不占用上下文长度
  - 314B 是等效知识容量；因稀疏激活，其实际计算占用与"激活的 0.5B"挂钩

#### ⚠️ 核心创新留白（本项目的命门，必须自主探索）

**"查"这项机制——如何寻址、如何存储 628 个知识块、如何快速调取、如何注入激活路径、如何与主参数联合训练——业界没有现成方案可参考，本项目也尚无实现先例。**

- **不预设任何实现方式**。上文提到的"内存级加载"只是类比，**不代表它真的从内存加载**；不得据此臆断成"预取 / 量化 / 分层缓存"等任何一种具体技术。
- **具体方案由你（Agent）自主设计并给出数学证明**。这是本项目最核心的创新点之一，是最重要的"留白考题"。
- 你需要设计的目标是：**在激活量极小（~0.5B）的前提下，让 628 个 0.5B 知识块的整体等效容量（314B）可被高效寻址与调取，且调取速度足够快、知识足够"有知识"（能支撑下游能力与评测）**。如何达到，由你决定。

#### 关键设计约束
- 计算（7B 主参数）和查找（314B 知识块池）**都是同一个模型的权重**——不是"模型 + 外部库"，而是"一个模型内部的激活部分与知识块池"
- "算"是模型权重的**激活态（主参数）**；"查"是**由 628 个 0.5B 知识块组成、每次仅稀疏激活 ~0.5B 的权重池**
- 被激活的知识块**参与训练**（不是"永不训练的冻结块"）
- 所有"活"的能力（推理、理解、创新、Agent）都在计算部分
- 现有的 `subconscious.py`（YvSubconsciousSystem）已体现"潜意识"思想，是查算分离的基础，在此基础上进行创新升级
- **寻址/存储/调取/注入/训练隔离的具体机制是未定项，属于必须自主创新的留白，不得照搬任何外部现成方案，也不得臆断为某种特定实现**

> **一句话理解**：算 = 意识（7B 主参数，全部激活参与计算）；查 = 潜意识（628 个 0.5B 知识块组成的 314B 池，每次稀疏唤起 ~0.5B，被唤起的块参与训练）。"内存"只是比喻，真正的寻址与调取机制是本项目必须自主发明的核心创新。

### 3.3 模态重定义与统一

#### 3.3.1 模态重定义（重大方向修正）

经过近半年的实践，团队认为原先的模态设计方向存在错误。**升级后的模态体系只保留 4 种真正的模态**：

**保留的模态（4 种）**：
- **text（文本）**
- **image（图片）**
- **audio（音频）**
- **video（视频）**

**移除的模态（2 种）**：

1. **document（文档）不再作为独立模态**
   - 理由：文档本质上可以通过 Agent 能力进行处理，不需要专门的文档模态编码器。文档的解析、理解、问答都可以走"Agent 操作 + 文本处理"的路径
   - 处理方式：删除 `YvDocEncoder`（LayoutLMv3）及相关文档模态代码，文档能力通过 Agent/文本能力间接覆盖

2. **agent（智能体）不再作为独立模态**
   - 理由：**Agent 本质上还是文本（TXT）**——它只是通过**标签（tag）的方式来操作 Agent 工具**，而不是一种独立的输入模态。这正是当前主流大模型（DeepSeek、GPT、Claude、Qwen 等）的做法：工具调用以特殊 token / XML 标签 / JSON 结构的形式出现在文本序列中，由模型自回归生成。半年的实践证实，把 Agent 当作独立模态是错误的设计方向
   - 处理方式：删除 `YvAgenticEncoder` 作为"模态编码器"的定位，Agent 能力回归为**文本层面的工具调用协议**（特殊 token / 标签 / 结构化文本），与主流方案对齐。已有的工具执行、ReAct、协议适配等推理时能力保留，但它们服务于"文本+工具调用"，而不是"agent 模态"

> **你需要注意**：在动手前，先查资料确认——查阅 DeepSeek、GPT、Claude、Qwen、Kimi 等旗舰模型的工具调用机制，确认 Agent 本质上是文本（标签驱动的工具调用），Document 的处理路径。用事实支撑这一重定义。

#### 3.3.2 模态统一

当前有多个独立模态编码器（vision, audio, video, doc, agentic），需要统一。经过 3.3.1 的重定义后，**只需为 4 种真正的模态（text/image/audio/video）做统一**：

**目标**：设计一个统一的多模态处理框架，消除模态间的冗余，同时保留各模态的特异性处理。

**你可以考虑的方向**（但不限于此）：
- 统一 token 空间：所有模态投影到共享的表示空间
- 统一编码器骨干 + 模态特异性适配器
- 统一融合机制：替代当前多个独立 fusion 模块（fusion, enhanced_fusion, rca_fusion, sync_fusion）
- 模态路由：MoE 天然支持模态特异性专家路由

**约束**：
- 必须支持 4 种模态（text, image, audio, video）
- 不能丢失任何模态的能力
- document 与 agent 的能力不能丢失——它们分别通过 Agent 能力 / 文本工具调用能力覆盖
- 所有模型规模（0.5B ~ 1T）都支持所有模态
- 彻底移除 document 和 agent 作为独立模态的痕迹（编码器、配置项、数据管线、评测项等）

### 3.4 上下文长度

**7B 模型的上下文要求**：
- **输入上下文**：≥ 1,048,576 tokens（1M）
- **输出上下文**：≥ 1,048,576 tokens（1M）
- 输入和输出都必须达到 M 级（百万级）

**其他模型规模**：

- 更小的模型（0.5B, 1.5B）可以适当降低上下文长度
- 更大的模型（32B+）应支持更长的上下文

### 3.5 思考/推理能力

**所有模型规模都必须支持思考能力（thinking/reasoning）**。这是与顶尖模型竞争的基础，不支持思考能力的模型没有竞争力。

现有的推理系统（`model/reasoning/`）包括：

## 七、T4 硬件约束

### T4 规格
- **GPU**：NVIDIA Tesla T4
- **显存**：16GB GDDR6
- **架构**：Turing（compute capability 7.5）
- **Tensor Core**：支持 FP16，不支持 BF16 原生加速
- **带宽**：320 GB/s

### 6.1 训练要求

**7B 模型必须在 T4 上进行完整、全精度、快速的训练。**

- **全精度**：训练应使用 FP16 或 BF16 精度（不使用 INT4/INT8 量化训练作为主要方式），确保训练质量
- **完整训练**：能完成完整的训练流程（前向、反向、优化器更新）
- **快速**：训练速度应尽可能快，通过架构设计和工程优化实现

**你必须解决的挑战**：
- 7B 参数 × FP16 = 14GB 权重，加上梯度和优化器状态，16GB 显存极其紧张
- 需要创新的内存管理：GaLore、梯度检查点、CPU 卸载、混合精度、选择性冻结
- 可能需要架构层面的创新：使模型在训练时显存占用最小化
- Flash Attention 在 Turing 架构上可能受限，需要替代方案

**鼓励的技术方向**：
- GaLore（低秩梯度投影）
- 梯度检查点（Gradient Checkpointing）
- CPU Offloading（优化器状态卸载到 CPU）
- 混合精度训练（FP16 + FP32 主权重）
- 选择性层冻结 + 渐进解冻
- LoRA / QLoRA 微调支持（作为可选模式，非唯一模式）
- 任何你发明的创新技术

### 6.2 推理要求

**7B 模型必须在 T4 上实现完美推理。**

- **完美推理**：高质量输出，无损精度，支持全部模态和全部上下文长度
- **1M 上下文推理**：KV Cache 管理（Paged Attention, 量化 KV Cache, 滑动窗口 + 混合策略）
- **314B 知识块池（查）**：模型自身权重，由 628 个 0.5B 知识块组成，推理时稀疏激活约 0.5B 量级，不将全部 314B 常驻激活显存；被激活的知识块以注入方式短暂影响激活路径，用完退回非激活态。**具体调取机制是本项目必须自主发明的核心创新（业界无现成参考），不得预设为 mmap / codebook / 预取等任何特定实现**——本质是调取模型自身的知识块权重，不是查询外部数据库
- **快速生成**：Speculative Decoding, Medusa, 或其他加速技术
- **量化推理**：4-bit / 8-bit 量化推理支持，但不作为唯一模式

```

         ↑                                                              ↓
         └──────────────── 直到全部达标才停止 ─────────────────────────┘
```

#### 迭代要求

1. **自主驱动**：不需要人指示，你自己发现问题、自己提出改进方案、自己验证
2. **创新驱动**：每次迭代必须是"实质性的架构/算法创新"，不是简单调参
   - 禁止：只调学习率、只改 batch size、只换优化器参数
   - 必须：改架构、换机制、引入全新算法、重新设计数据流
3. **永不降标**：达不到目标时，只能向上迭代（提升能力），禁止下调目标
4. **记录留痕**：每次迭代必须留痕——假设、改动、结果、分析、下一步
5. **收敛判据**：只有当所有硬性指标（8.1~8.4）全部达标，迭代才结束
6. **迭代上限**：没有上限。你需要多久就迭代多久，直到达标

#### 创新的定义（必须区别于"优化"）

| 范畴 | 不算创新（禁止拿来交差） | 算创新（必须做到） |
|------|------------------------|-------------------|
| 架构 | 调整层数/维度/头数 | 重新设计 MoE 路由/查算分离注入/模态统一框架 |
| 算法 | 调学习率/换优化器 | 发明新的注意力/寻址/融合机制 |
| 实现 | 加个 wrapper/换名 | 相同能力下数量级的效率提升 |
| 系统 | 调 batch/精度 | 全新的显存管理/知识调取方案 |

**一句话：优化是在已有轨道上跑得更快，创新是铺一条新轨道。你必须铺新轨道。**

### 8.6 评测执行要求

- 所有评测**必须真实运行**，禁止使用预存结果或模拟分数
- 评测脚本必须可复现：任何人拿到代码后可以在 T4 上复跑
- 评测结果需附完整日志（输入/输出/分数/耗时）
- 与 DeepSeek-V4-Flash-0731 的对比需在相同评测条件下进行
- 缺失的评测项（如平台不支持）需明确说明原因，不能跳过
- **每轮迭代的评测结果都必须归档留痕**，形成完整的迭代轨迹

### 8.7 强制性数学证明要求（核心要求）

**你的每一项创新——无论是新架构、新算法、新机制——都必须附带严格的数学证明。**

这不是"写几句解释"，而是**真正的数学证明**。拍脑袋说"这样应该更好"是不允许的。

#### 8.7.1 必须证明什么

1. **正确性证明**：证明你的机制在数学上是正确的
   - 复杂度分析：时间/空间复杂度的严格推导（大 O 记号）
   - 收敛性证明：如果涉及优化/训练过程，需证明或引用收敛性结论
   - 梯度稳定性：如果是可训练模块，需分析梯度是否存在爆炸/消失风险（如雅可比谱分析、Lipschitz 常数界）
   - 数值稳定性：浮点误差分析，说明为什么不会数值溢出/下溢
2. **有效性证明**：证明你的机制为什么能提升能力
   - 表达能力：证明它比被替代的旧机制表达力更强（或至少不弱）
   - 信息论分析：如涉及知识注入/压缩，需用信息论（互信息、熵、率失真）说明信息损失下界
   - 建模假设：明确前提假设，并在假设下证明结论
3. **必要性/最优性论证**：证明为什么必须这么做
   - 如果声称某个设计是吞吐/显存最优的，需要推导出下界并证明达到下界
   - 如果声称某个容量（如 314B 等效）是紧凑的，需要证明压缩效率的理论极限
4. **与现有方法的对比证明**：数学上说明你的方法为何优于现有论文的方法

#### 8.7.2 证明的强制标准

- **证明必须正确**：逻辑无漏洞、无循环论证、每一步都有依据。**错误的证明等同于没有证明，甚至更糟**
- **证明必须真实**：禁止编造定理、禁止伪造推导、禁止"证明显然成立"式的敷衍、禁止引用不存在的论文
- **证明必须可验证**：任何人能按你的推导逐步复核。每一步推导都要写清楚依据（定义/引理/定理/已知结论）
- **证明必须留痕**：所有证明必须以 Markdown 形式写出，归档到对应文件夹（如 `docs/proofs/` 或对应模块目录下），并注明对应的代码实现位置

#### 8.7.3 证明与实现必须绑定

- 每一个创新点：**数学证明 ↔ 代码实现** 必须一一对应，可互相追溯
- 如果代码实现与证明不符（如实现做了额外近似），必须明确说明近似的位置、误差界、以及为什么可接受
- 提交前必须自查：证明的结论是否真的被代码实现？实现是否真的满足证明的前提？

#### 8.7.4 不符即不通过

- **证明错误的创新点不予采纳**：如果某个机制的证明存在逻辑错误，必须修订机制或证明，直到正确为止
- **无证明不算创新**：任何声称的"创新"如果没有配套的、正确的数学证明，一律不算创新，不能作为验收依据

### 8.8 自主架构探索：不只是 MoE（核心要求）

**MoE 稀疏专家只是"当前已知的一条路径"，绝不是唯一路径。** 未来的架构不会只有 MoE 一条路。你被授权并鼓励**自主探索、自主发明全新的架构范式**。

#### 8.8.1 你必须自主探索

- **不被现有架构束缚**：允许跳出 MoE 的框架，探索全新的参数组织方式
- **允许自主增加架构组件**：如果现有架构不足以支撑目标（如 7B 逼近旗舰、1M 上下文、T4 全精度训练），你可以自主新增架构组件——全新的模块、全新的计算范式、全新的参数组织
- **允许自主开辟新路径**：MoE、查算分离、SSM、混合注意力……这些都只是"已知地图"上的点。你有权去地图之外探索

#### 8.8.2 但不允许冗余

自主探索和增加**必须在"不冗余"的前提下进行**，这是硬约束：

- **禁止功能重叠**：新增的架构组件不能与已有组件功能重复（例如不能同时存在两个作用相同的路由机制）
- **禁止堆砌**：不能为了"看起来创新"而加入无意义的组件。每个组件必须有其不可替代的作用
- **合并优先**：如果新思路与旧组件重叠，应合并升级，而不是并存
- **正交设计**：理想情况下，各组件应是正交的、互补的，各自负责不同的能力维度

#### 8.8.3 目标：既精简又强大

- **不冗余**（避免堆砌、功能重叠、参数浪费）
- **强能力**（充分发挥每一份参数的潜力，能逼近旗舰、能支撑全模态、能处理 1M 上下文）

**真正的进化 = 在不冗余的前提下发挥出更强大的能力。** 只增加组件叫堆砌，只做减法叫退化，**既做加法又做减法、在更精简的结构里爆发出更强的能力，才叫进化**。

这两条（"自主探索新路径" + "绝不冗余"）必须同时满足，缺一不可：
- 只堆砌不精简 → 违背不冗余原则
- 只精简不探索 → 违背创新要求
- **又精简又强大** → 这才是被期待的进化

#### 8.8.4 MoE 仍然必须保留

探索新路径**不意味着抛弃 MoE**：
- 所有模型规模（0.5B ~ 1T）**仍然必须是 MoE 稀疏专家模型**（见第三章、禁止事项）
- MoE 是最底层的基础，你可以在这个基础之上**叠加、组合、发明**新的架构范式
- 允许的探索包括：与 MoE 正交的新组件、MoE 之上的新组织方式、超越 MoE 的新范式（但必须保证 MoE 特性——稀疏专家激活——不被破坏）

## 十三、强制创新要求

本任务**强制要求全面创新**，不是可选的加分项，而是核心验收标准。

### 13.1 创新是硬性要求

- 你不仅要优化和升级，还必须**发明新的机制、新的算法、新的架构设计**
- 简单地将现有算法从论文复制到代码中**不算创新**——你需要在理解原理的基础上进行改进、组合、或发明全新的方法
- 特别是在 T4 约束下，如果现有技术无法满足要求，你必须**发明新的解决方案**

### 13.2 创新方向（不限于此）

- **架构创新**：重新设计 MoE 路由机制、查算分离的注入方式、模态统一框架
- **算法创新**：改进注意力复杂度、KV Cache 管理、训练内存优化、推理加速
- **系统创新**：T4 上的显存管理新方案、314B 知识块池的寻址/调取机制创新
- **融合创新**：将多个已有技术进行非平凡的组合，产生新的能力
- **理论创新**：如果有数学上的新发现或推导，鼓励探索

### 13.3 创新验证

- 每个创新都必须有**严格的数学证明**（详见 8.7）支撑，证明必须正确、真实、可验证
- 每个创新必须有**实验验证**（在 T4 上真实运行）
- 不能凭空声称"创新了"——必须有可复现的证明与效果
- 创新点必须在架构设计文档中明确标注，并说明与现有方法的区别和优势

### 13.4 创新与"优化"的严格区分（不可混淆）

**本任务不接受"优化"冒充"创新"。** 优化是在已有轨道上跑得更快；创新是铺一条全新的轨道。

| 维度 | 优化（不达标，禁止交差） | 创新（必须做到） |
|------|------------------------|-----------------|
| 架构 | 调层数、维度、头数、专家数 | 重新设计模型的组织范式/信息流 |
| 算法 | 调超参、换优化器、换激活函数 | 发明前所未有的机制/结构/运算 |
| 实现 | 加 wrapper、换名字、拼接口 | 相同能力下的数量级效率跃升 |
| 系统 | 调 batch、精度、并行度 | 全新的显存/调度/寻址方案 |

**判定标准**：如果你能在一篇现有论文里找到完全相同的做法，那就不是创新。创新必须是"查不到先例"或"有实质性的非平凡改进"。

### 13.5 创新是进化的唯一路径

高目标（见 8.4）的唯一目的，就是**逼出进化**。分数定得低，你不会创新；分数定得高，你不得不创新。

- 目标是接近 DeepSeek-V4-Flash-0731 的真实水平（85%~95%）
- 靠"优化"不可能达到这个水平——因为 7B 的参数量远小于对手
- 唯一的出路是：**用全新的架构、全新的算法、更优的实现，实现质的跃迁**
- 这就是"进化"：不是把现有东西做得更好一点，而是变成更强的物种

### 13.6 自主架构探索：不止 MoE 一条路

**未来的架构不会只有 MoE 一条路径。** 你必须自主探索、自主开辟新的路径，而不局限于已知的架构范式（详见 8.8）。

- **自主探索**：MoE、查算分离、SSM、混合注意力只是"已知地图"上的点。你有权去地图之外探索全新范式
- **自主增加**：如果现有架构不足以支撑目标，你可以自主新增架构组件——新模块、新计算范式、新参数组织方式
- **绝不冗余**：探索与增加必须在"不冗余"前提下进行——禁止功能重叠、禁止堆砌、合并优先、正交设计
- **既精简又强大**：真正的进化 = 在更精简的结构里爆发出更强的能力。只加叫堆砌，只减叫退化，**又加又减、精简而强大才叫进化**
- **MoE 是底线**：探索不等于抛弃 MoE。所有规模仍须是 MoE 稀疏专家模型，MoE 是基础，你在此基础上叠加/组合/发明新范式

**这是进化中的一条核心路径：自主探索 + 自主增加 + 绝不冗余 = 更强的物种。**
